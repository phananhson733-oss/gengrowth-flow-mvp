# GenGrowth Agent Harness Review Checklist

这份清单用来判断一个 Agent 方案是不是只会“演示”，还是能稳定完成真实任务。它把 Harness（让模型可靠工作的工程外壳）拆成目标、工具、上下文、任务闭环、记忆、评估、安全和资产沉淀 8 个检查面。

> [!info] 一句话结论
> GenGrowth 当前不缺“再做一个 Agent”的想法，缺的是一套能反复判断 Agent 是否可交付、可维护、可产品化的评审标准。这份 Checklist 就是 PM 评审门。

## 1. 为什么现在需要这张表

DeepSeek 招聘 Agent Harness 产品经理释放了一个信号：头部模型公司的竞争焦点正在从“模型能力”转向“模型 + Harness = Agent 产品”。

对 GenGrowth 来说，真正有价值的不是追新闻，而是把这个信号转成内部可用的产品评审框架：

| 变化 | 对 GenGrowth 的含义 |
|---|---|
| Agent 不再只是 Prompt | 需要产品、工程、数据、UX 一起评审 |
| 真实任务反馈变重要 | AI 日报、剪藏、Kanban、Ops 执行都应变成评估样本 |
| Harness 成为岗位能力 | 彪哥需要一套 Agent PM 的判断语言和验收标准 |
| 模型能力持续变化 | Harness 组件要定期删减，不是越复杂越好 |

## 2. 适用对象

| 用户 | 使用场景 | 产出 |
|---|---|---|
| 彪哥 / PM | 评审一个 Agent 产品、工作流或服务包是否值得推进 | P0/P1/P2 判断、验收标准、风险清单 |
| Hermes / BotOps | 检查多 Bot、cron、Kanban、消息入口是否稳定 | 工程改进任务、监控项、回滚方案 |
| Ops | 执行低风险资料整理、反馈标注、素材归档 | 执行单、标注表、问题反馈 |
| 玲姐 / CEO | 判断是否产品化、是否投入资源、是否对外承诺 | 决策选项、风险说明、推荐方案 |

## 3. 使用方式

每评审一个 Agent 方案，按 8 个关卡打分：

- 0 分：没有证据，只是想法。
- 1 分：有 demo，但依赖人工兜底。
- 2 分：有流程和样本，能稳定跑小范围任务。
- 3 分：有验收、日志、权限、安全和复盘，能进入产品化试点。

> [!tip] 推荐门槛
> P0 MVP 不要求每项 3 分，但“目标用户、任务闭环、人工审核、安全边界”必须至少 2 分；否则不应进入自动化或客户交付。

## 4. 八关评审表

### 4.1 目标与用户

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 用户是谁 | 能说清是 PM、Ops、客户、开发者还是内容团队 | 用户画像、真实对话、需求来源 |
| 场景是否真实 | 有 3 个以上真实任务样本，不只是想象场景 | 任务记录、聊天记录、工单、剪藏样本 |
| 痛点是否高价值 | 节省时间、降低错误、提高转化或沉淀资产 | 当前人工流程耗时、错误率、机会损失 |
| 替代方案是否存在 | 知道不用 Agent 时怎么做 | 人工 SOP、表格、脚本、Zapier/Make 等 |

PM 判断：如果用户和场景说不清，不要进入 Harness 设计，先回到需求澄清。

### 4.2 模型与工具

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 模型能力边界 | 知道哪些任务模型能独立完成，哪些必须人工确认 | 试跑样本、失败案例 |
| Tool Use | 工具权限最小化，能解释为什么需要每个工具 | 工具清单、权限说明 |
| 外部系统连接 | Slack、微信、飞书、GitHub、wiki、gbrain 等连接有明确用途 | 配置说明、调用日志 |
| 失败回退 | 工具失败时能降级，不会静默误报成功 | 错误处理、重试策略、人工提醒 |

PM 判断：工具越多不代表能力越强，工具不可控会放大风险。

### 4.3 上下文与输入

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 输入结构 | 用户输入、系统资料、历史资产分层清楚 | 输入模板、字段定义 |
| 上下文来源 | 能区分事实、假设、旧记录和当前用户指令 | 引用路径、来源标注 |
| 压缩策略 | 长任务有 handoff，不靠模型“记住” | 任务摘要、artifact、记录文件 |
| 噪音控制 | 不把无关历史塞进上下文 | 检索规则、过滤规则 |

PM 判断：Agent 的很多错误不是模型不会，而是上下文脏、乱、过期。

### 4.4 任务闭环

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 任务入口 | 用户知道从哪里发起任务 | Slack 频道、微信入口、Kanban 卡 |
| 负责人 | 玲姐、彪哥、Ops、Hermes 分工明确 | RACI 或任务卡 |
| 状态流转 | todo / running / blocked / done 可追踪 | Kanban、日志、消息回执 |
| 完成定义 | 有验收标准，不是“我觉得做完了” | Checklist、测试、人工确认 |
| 反馈闭环 | 失败原因能回流到 SOP / Skill / wiki | 复盘文档、skill patch、日志 |

PM 判断：没有状态和验收的 Agent，只是聊天助手，不是可交付系统。

### 4.5 记忆、Skills 与资产沉淀

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 长期记忆边界 | Memory 只存稳定偏好和规则，不存大量客户资料 | memory 条目审查 |
| Skill 复用 | 高频流程沉淀成 Skill 或 SOP | SKILL.md、模板、脚本 |
| wiki / gbrain | 重要判断可检索、可复用、可追溯 | wiki 页面、gbrain slug |
| 查重机制 | 新建资产前能搜索已有内容 | search / gbrain 记录 |

PM 判断：沉淀不是“写一篇漂亮文档”，而是下次 Agent 能少犯错、少问人。

### 4.6 评估与可观测性

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 任务成功率 | 至少定义 1 个核心成功指标 | 完成率、返工率、人工介入率 |
| 质量评估 | 主观任务拆成可评分维度 | 评分表、样例对比 |
| 日志可查 | 成功、失败、工具错误、人工确认都有记录 | run history、log、record |
| 独立评审 | 执行者和评审者分离 | reviewer、QA、人工验收 |

PM 判断：不能只看“输出像不像”，要看它在真实任务里是否稳定减少人工成本。

### 4.7 权限、安全与合规

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 权限最小化 | Ops / PM / CEO 权限边界清楚 | 权限说明、工具集配置 |
| 高风险确认 | 外发、删除、改配置、客户承诺等必须人工确认 | 确认记录、审批流程 |
| 敏感信息 | 不泄露 token、私有 memory、跨 bot 私密上下文 | 安全审查 |
| 可回滚 | 自动化出错能停用或恢复 | cron/job 配置、备份 |

PM 判断：Agent 越接近真实业务，权限边界越重要；不能为了自动化牺牲可控性。

### 4.8 产品化与服务化

| 检查项 | 通过标准 | 证据 |
|---|---|---|
| 复用性 | 不是只为一次任务定制 | 模板、标准流程、配置项 |
| 服务包边界 | 能说清交付范围、周期、客户输入和验收 | 服务包草案 |
| 定价价值 | 能对应节省成本、提升转化或降低风险 | ROI 假设、客户访谈 |
| MVP 路线 | 先做最小可验证版本，不一开始全自动 | P0/P1/P2 路线 |

PM 判断：能产品化的不是 Agent 本身，而是“诊断 + 搭建 + 验收 + 复盘”的交付闭环。

## 5. GenGrowth 当前建议的 P0 MVP

先用这张表评审一个内部真实场景：AI Builder 情报从链接到产品机会的处理流程。

| 阶段 | 做什么 | 验收标准 |
|---|---|---|
| P0 | 选 10 篇 AI Builder / Harness / Agent 文章，按本 Checklist 做评审 | 每篇都有用户、场景、机会、MVP、风险、下一步 |
| P0 | 把评审结果沉淀到 wiki / gbrain | 10 篇可搜索，至少 3 篇转成产品机会 |
| P0 | 生成一个 Agent Harness Review 模板 | PM 可直接复制给 Ops 或 Hermes 使用 |
| P1 | 把模板接入 Kanban 任务卡 | 每个 Agent 实验都有负责人、验收和状态 |
| P2 | 面向客户包装成服务包 | 形成“Agent 工作流体检 + Harness 设计 + MVP 验收”交付说明 |

## 7. 角色分工

| 角色 | 负责什么 | 不负责什么 |
|---|---|---|
| 玲姐 | 是否产品化、是否投入资源、客户/定价/战略边界 | 不处理日常评审表填写 |
| 彪哥 | 定义评审标准、排序机会、拆 MVP、验收结果 | 不替 CEO 做公司级决策 |
| Ops | 收集资料、整理样本、按模板标注、反馈执行问题 | 不判断产品路线和商业策略 |
| Hermes | 自动化抓取、任务流转、wiki/gbrain 沉淀、日志 | 不越权读取私密上下文 |

## 8. 红线提醒

- 不要把媒体报道里的招聘、融资、估值当官方事实对外引用。
- 不要因为 DeepSeek 提到 Harness，就把所有 GenGrowth 自动化都包装成“Agent 产品”。
- 不要上来就做多 Agent 大系统，先用 10 个真实任务样本验证。
- 不要让执行 Agent 自己宣布自己完成，必须有独立评审或明确验收。
- 不要用 Hermes memory 存客户档案、敏感数据或大段任务记录。

## 9. 下一步

1. 彪哥：用这张表评审 1 个现有内部 Agent 流程，建议从“微信公众号链接剪藏 → PM 判断 → wiki/gbrain 沉淀”开始。
2. Ops：按模板整理 10 个近期 Harness / Agent 素材，每条补来源、场景、可转化机会。
3. Hermes：把高频评审字段做成 Kanban 子任务模板，后续每个 Agent 实验都走同一套验收。
4. 玲姐：只在出现“是否对外产品化 / 是否投入服务包资源 / 是否涉及客户承诺”时决策。
