# GenGrowth 内部增长 MVP — Ops/PM 简版

> 这份文档是给 **不写代码的人**（Ops、PM、合作伙伴、未来招的小伙伴）看的。
> 它回答 4 个问题：**做什么 / 为什么 / 谁做 / 多久多少钱**。
> 技术细节、数据表字段、代码接口都在配套的 v1.2 技术版里，本文不展开。

---

## 1. 一句话总结

> 我们要在 **5 周**内，把 astrologywiki.com 的"找词 → 写文 → 发布 → 数据复盘"这条 SEO 内容生产线，从**全手工**变成**半自动**（关键决策仍由 wzb 拍板），让单人产能从约 14 篇/周提升到 **可持续 14-25 篇/周**，并把数据回收做到每周自动出报表。

---

## 2. 为什么做 / 业务目标

### 2.1 当前痛点

- wzb 一个人扛全部内容生产，手工流程把审稿、找词、复盘绑死，**没有时间做新产品**
- 5 篇精选文章 + 量产线 Aura 1A 都没有标准化数据回收，**Day 14 / Day 30 该刷新还是该砍不知道**
- 想 onboard 第二个产品（未来 30-60 天）时，**没有可复用的工具栈**

### 2.2 60-day 业务目标（来自 PRD v0.7）

- PV 增长目标见 PRD §1.1（具体数字 wzb 内部锁定）
- 每周内容产出从 5-7 篇 → **稳定 14 篇/周**
- 每周一份自动周报：哪些文章在涨、哪些该刷新、哪些该砍

### 2.3 成功标准（5 周末验收）

| 维度 | 验收标准 | 怎么测 |
|------|----------|--------|
| 产能 | 5 周稳定产出 ≥60 篇 | 数文章数 |
| 工时 | wzb 每周投入 ≤32 小时（红线） | 每周自报 |
| 质量 | 单篇返工时间下降 ≥30%（vs Week-1 手工对照） | Week-3 末做对照实验 |
| 成本 | 月度外部 API 支出 ≤$150 | 月底对账 |
| 数据可见性 | 每周一自动周报到邮箱 / Telegram | Week-5 起跑 |

## 3. 范围 / 我们要建什么、不建什么

### 3.1 建：6 个 Skill + 几段半自动脚本

| Skill | 解决的问题 | 上线周次 |
|-------|-----------|---------|
| 🔍 找词工具 | 给 100 个种子词，自动扩成 800+ 候选 + 难度/搜索量评分 | Week-2 |
| ✍️ 写文工具（基础版） | 给一个选题 + Tier，自动出一篇可审草稿 | Week-3 |
| ✍️ 写文工具（精修版） | 加入跨模型挑战、心理安全检查、深度取证 | Week-4 |
| 📊 数据回填工具 | 每周一自动从 GSC / GA4 拉数据，写复盘表 | Week-4 |
| 🔗 集群工具 | 把 800 个词分到 20-30 个内容簇 | Week-5 |
| 📰 周报 / 刷新工具 | 周报 + Day 14/30/60 决策建议 | Week-5 |

### 3.2 不建（暂留手工，PM 不用纠结）

- **PGB 写作**（每次进新主题前的 6 字段背景调研）—— 这是 wzb 个人创造性工作，工具化没价值
- **技术 SEO 闸门**（页面性能 / canonical / robots / hreflang）—— 一次性检查，跑工具不如手动 checklist
- **社媒分发**（X / Reddit / Threads）—— 内容标题和图都是创意活，半自动会降质
- **退场决策**（哪个文章砍）—— 工具列清单，wzb 拍板

### 3.3 边界外（v1.3 才考虑）

- 第二个产品 onboard
- 深度报告生成（订阅产品的核心交付，目前未启动）
- Newsletter double opt-in（合规升级）
- 自动 A/B 测试

## 6. wzb 每周工时表（核心约束：≤ 32 小时/周红线）

| 周 | 审稿 | 运营 | 工程管理 | 决策/PGB | **合计** | 状态 |
|----|------|------|----------|----------|----------|------|
| Week-1 | 11h | 2h | 0h | 4h | **17h** | ✅ |
| Week-2 | 5h | 3h | 6h | 2h | **16h** | ✅ |
| Week-3 | 8h | 4h | 8h | 2h | **22h** | ✅ |
| Week-4 | 8h | 5h | 12h | 2h | **27h** | ✅ |
| Week-5 | 6h | 4h | 8h | 2h | **20h** | ✅ |

**红线机制**：任一周 wzb 实际投入超过 32h → 自动触发**降级**（详见 §8）：停下工具开发，只做内容产出，工具推迟一周。

**关键假设**：工程管理时间 = wzb 给 Claude Code 出方向 + 看 PR + 跑测试的时间，**不是 wzb 自己敲键盘的时间**。如果改成 wzb 自写，全表数字翻 3-4 倍，5 周计划做不完。

## 9. 数据安全与隐私（PM 友好版）

| 关注点 | v1.2 做法 |
|--------|----------|
| 用户搜索词（GSC query） | 默认不存原始，启用时脱敏 7 类（邮箱/电话/姓名/出生日期/健康/地址/财务） |
| Service Account 密钥 | 三把密钥（读/写/管），按权限最小化；管理员密钥默认禁用 |
| 第三方网站内容（Reddit / Quora） | 走过滤器：黑名单域名 + 注入语句剔除 + 内容隔离（不作为 AI 指令） |
| oracle 仓库写入 | 工具只写"暂存区"，wzb 手工 review + merge（不直推 prod） |
| 心理安全（健康类内容） | 全 Tier 基线检查 + 精修线加全 SOP（不诊断、不替代专业） |

## 12. FAQ（Ops/PM 常问）

**Q：为什么是 5 周，不是 3 周或 8 周？**
A：5 周是 wzb 32h/周红线下能稳定 ship 6 个工具的最小周数；3 周做不完（codex 评估），8 周内容产出会因工具开发挤压而下滑。

**Q：能不能跳过对照实验直接上工具？**
A：不能。如果工具产出草稿仍要 45 min/篇返工，那工具就是负价值。Week-3 末对照实验是 go/no-go gate。

**Q：万一 wzb 病了 / 出差怎么办？**
A：所有手工 SOP（写文 / 审稿 / 发布 / 周报）都写在文档里，未来招小伙伴可上手。工具本身也都支持 `--dry-run`，可以让助理 / 实习生先跑预览，wzb 远程审。

**Q：v1.2 跟 v1.0 / v1.1 什么关系？**
A：v1.0 是初稿，v1.1 修了 v1.0 的 26 项问题但过度修复（引入了不必要的抽象层），v1.2 砍掉过度抽象 + 修对了之前的数据表对账漂移，**v1.2 是当前唯一可实施版本**。

**Q：60 天后我们应该看什么数字判断这套工具是否成功？**
A：3 个数字：①wzb 每周工时是否守住 32h；②周产出是否 ≥14 篇；③Day 30 自然搜索 PV 是否在涨。三个都达成 → 工具成功。

**Q：第二个产品 onboard 需要多久？**
A：v1.2 设计是"改一份配置文件 + 备一套模板"，预计 2-3 天准备 + 1 周磨合。v1.3 才会上正式的"产品抽象层"。

**Q：如果 wzb 一个人扛不住，找助理能分担什么？**
A：从易到难：① 发布回填的 git 机械操作（M9 SOP，~1.5h/周）→ ② 关键词数据复盘 → ③ T3 草稿审稿（红线检查通过的）→ ④ 社媒分发。审 T1 文章 / 拍板止损 / 产品决策 wzb 必须自己来。
